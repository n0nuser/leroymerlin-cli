---
title: exit codes
description: A small set of statuses you can branch on, and which ones are worth a retry.
---

Nothing is printed to stdout when a command fails, so a script can read stdout and
`$?` independently.

| code | meaning | retry? |
| --- | --- | --- |
| `0` | success, including "nothing changed" | - |
| `1` | generic failure | maybe |
| `2` | usage: bad flags, unknown key, missing argument | no, fix the call |
| `3` | auth: no session, expired session or a rejected import | no, import again |
| `4` | not found: unknown store, category or product | no |
| `5` | blocked: bot protection challenged the request, or it was rate limited | yes, after a pause |
| `6` | network: timeout, DNS failure, proxy unreachable | yes |
| `7` | the site answered with a shape the cli does not understand | no, report it |
| `130` | interrupted with Ctrl-C or SIGTERM | - |

## retrying

Back off on `5` and `6`, and stop on the rest:

```bash
leroymerlin watch check --all
case $? in
  0) ;;
  5) sleep 900 && leroymerlin watch check --all ;;
  6) sleep 60 && leroymerlin watch check --all ;;
  *) exit 1 ;;
esac
```

A `5` means the challenge page came back instead of the storefront. Wait, reload
leroymerlin.es in the browser, export the cookies again if it keeps happening, and do
not hammer the same endpoint.

A `7` is not a transport problem. The request worked and the answer did not match what
the parser expects. Include the printed issue link when you report it.

## the error envelope

`--error-format json` prints a single JSON object on stderr with the same `code`, a
stable `category`, `retryable` and, when relevant, `http_status`, `endpoint` and
`issue_url`. Use the category, not the message.

<Callout type="idea" title="branch on category">
  `usage`, `auth`, `not_found`, `blocked`, `network`, `api_changed` and `generic` are
  the categories. They map one-to-one onto the codes above, except code `1`, which is
  `generic`.
</Callout>
